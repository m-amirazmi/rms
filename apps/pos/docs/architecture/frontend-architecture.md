# POS Frontend Architecture

> Feature-based folder structure for the POS application.

---

## Philosophy

- **Routes are thin** — only TanStack Router wiring. No business logic.
- **Features are self-contained** — each feature owns its components, types, schemas, API, and utils.
- **Shared code lives in `components/`** — reusable layout components like `AuthTopbar`.
- **No cross-feature imports** — features communicate via router navigation or localStorage, not direct imports.

---

## Folder Structure

```
apps/pos/src/
├── features/               # Feature modules
│   ├── language/             # Global language store (EN/MY)
│   ├── wizard/               # Wizard progress store + step constants
│   ├── new-device/           # Device pairing flow
│   ├── select-staff/         # Staff selection + PIN overlay
│   ├── select-category/      # Step 1: Category selection
│   ├── select-brand-model/   # Step 2: Brand & model
│   ├── select-issues/        # Step 3: Issue diagnosis
│   ├── select-parts/         # Step 4: Parts selection
│   ├── customer-tech/        # Step 5: Customer & technician
│   └── repair-summary/       # Step 6: Review & submit
│
├── routes/                 # TanStack Router file-based routes
│   ├── (auth)/
│   └── (wizard)/
│
├── components/             # Shared layout + shell components
├── main.tsx
└── routeTree.gen.ts        # Auto-generated by TanStack Router
```

## Feature Module Anatomy

Every feature under `features/` follows this structure:

```
features/<feature-name>/
├── README.md               # Feature documentation
├── index.ts                # Barrel export — public API
├── types.ts                # TypeScript interfaces
├── constants.ts            # Mock data, magic numbers
├── schemas.ts              # Zod validation schemas
├── api.ts                  # Async functions (mock or real)
├── utils.ts                # Pure helper functions
└── components/
    ├── <feature-name>-page.tsx   # Main page component
    └── ...                       # Sub-components
```

### Rules

1. **Import from `index.ts` only** — external code never deep-imports into a feature.
2. **Route files import from features** — routes are pure wiring.
3. **Types use `import type`** — required by `verbatimModuleSyntax`.
4. **No `hooks/` folder unless reused** — hooks live inside the component that uses them. Extract only when shared across components.

## Example: Adding a New Feature

```bash
# 1. Create feature folder
mkdir -p src/features/my-feature/components

# 2. Create files
touch src/features/my-feature/index.ts
touch src/features/my-feature/types.ts
touch src/features/my-feature/schemas.ts
touch src/features/my-feature/api.ts
touch src/features/my-feature/components/my-feature-page.tsx

# 3. Create route
mkdir -p src/routes/(wizard)
touch src/routes/(wizard)/my-feature.tsx
```

Route file (`src/routes/(wizard)/my-feature.tsx`):

```tsx
import { createFileRoute } from "@tanstack/react-router"
import { MyFeaturePage } from "@/features/my-feature"

export const Route = createFileRoute("/(wizard)/my-feature")({
  component: MyFeaturePage,
})
```

## Shared Components

Components used by multiple features live in `src/components/`:

| Component | Used By |
|---|---|
| `AuthTopbar` | Auth screens (`new-device`, `select-staff`) |
| `TopBar` | Wizard shell — logo, breadcrumb, language toggle, avatar |
| `BottomNav` | Wizard shell — Previous / Continue sticky nav |
| `WizardShell` | Wraps all `(wizard)/` routes — responsive layout |
| `WizardBreadcrumb` | Desktop top bar + mobile scrollable row |
| `LanguageToggle` | Top bar — EN/MY language switch |
| `AvatarPopover` | Top bar — staff menu + cancel intake dialog |
| `SummaryPanel` | Desktop (`lg+`) — persistent right sidebar |
| `SummaryBar` | Tablet (`md`) — collapsible summary bar |
| `SummaryPeek` | Mobile (`<md`) — sticky bottom summary peek |

Features may import shared components. Shared components must never import features.

## Dependency Direction

```
routes/          → features/
features/        → components/
features/        → @workspace/ui/
components/      → @workspace/ui/
```

No arrow goes from `features/` → `features/` or `components/` → `features/`.

## Zustand Store Conventions

Stores are co-located inside the feature that owns the domain:

```
features/<feature>/
├── <feature>-store.ts    # Zustand store definition
├── index.ts              # Barrel export (re-exports store + types)
└── ...
```

### Rules

1. **Functional stores** — Use plain `(set, get) => …` creators. Avoid the heavy class-based action pattern unless the store grows beyond 10+ fields.
2. **Primitive selectors only** — Components must select primitives (numbers, strings, booleans) or stable function references. Never select computed objects/arrays from the store — they create new references on every call and trigger cascading re-renders.
3. **`persist` middleware** — Use Zustand's `persist` for data that must survive refreshes. Always `partialize` to only serialize necessary state.
4. **No `getSummary()` in stores** — Derived data should be computed in components using `useMemo` over primitive subscriptions, or read static mock data directly at module level.

### Example

```ts
// features/wizard/wizard-store.ts
import { create } from "zustand"
import { persist } from "zustand/middleware"

export const useWizardStore = create<WizardState>()(
  persist(
    (set, get) => ({
      currentStepIndex: 0,
      formData: {},
      // actions...
    }),
    {
      name: "rms_wizard",
      partialize: (state) => ({
        currentStepIndex: state.currentStepIndex,
        formData: state.formData,
      }),
    }
  )
)
```
